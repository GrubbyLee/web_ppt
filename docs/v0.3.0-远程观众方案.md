# Showit v0.3.0 方案：局域网与公网观众屏（中继服务）

状态：已实施（P2P 模式 + 本地中继端到端验证通过；SFU 模式为后续项）
日期：2026-09-29
前置：v0.2.x（WXT 纯扩展）。v0.1 的 `audience_service.rs`（axum HTTP/WS/SSE + 审批 + LiveKit SFU）是本方案的实现蓝图，经 `git show v0.1.0` 可考。

## 1. 目标与非目标

**目标**：演示方式 1 —— 演示者在自己的屏幕上运行业务窗口 + 控制台；观众用自己的浏览器（免装扩展）观看"观众屏"（业务系统只读画面），覆盖：

1. **局域网**：中继部署在内网任意主机，观众访问 `http://<内网地址>`；
2. **公网**：同一中继部署到云端（域名 + TLS），观众访问公网地址。

**非目标**：
- 不恢复 v0.1 的观众审批工作流之外的管理复杂度（踢出/质量统计降级为最小实现，见 §6）；
- 不做音频（产品一贯红线：无麦克风采集）；
- 不做多演讲者/多房间并发（单房间单演讲者，与演示场景匹配）；
- 不改变本机观众窗口（同一浏览器模型继续可用，且与远程观众并存）。

## 2. 核心架构

```
┌─ 演示者浏览器（扩展） ─────────────────────────────┐   ┌─ 中继服务（apps/relay） ──────┐   ┌─ 观众浏览器 ─┐
│                                                    │   │                              │   │ 免装扩展     │
│  background ──编排/房间管理/令牌──▶ relay (REST) ──┼──▶│  /health                     │   │              │
│  offscreen ──合成后的 WebRTC 流──▶ relay (WSS) ────┼──▶│  /api/rooms (创建/结束)      │   │  观看页      │
│    ▲ tabCapture→canvas 合成（遮罩/封面在源端强制） │   │  /watch/<房间码> 观看页      │◀──│  (静态资源)  │
│  sidepanel ──观众状态/断开操作─────────────────────┤   │  /signal/<…> (WS 信令)      │   │  RTCPeer-    │
└────────────────────────────────────────────────────┘   │  /events/<…> (SSE 快照)     │◀──│  Connection  │
                                                         │  SFU 上行（可选，>5 观众）    │   └──────────────┘
                                                         └──────────────────────────────┘
```

**关键决策**：

| # | 决策 | 理由 |
|---|---|---|
| D1 | 中继为**独立部署单元**（`apps/relay`，Node.js + TypeScript，单进程） | 扩展无法监听端口（平台边界）；Node 与现有工程栈一致，团队零新增语言成本；Docker 化后局域网/公网同一产物 |
| D2 | **隐私在源端强制**：offscreen 合成器先套遮罩/封面再编码上传 | 中继只见"已保护"的像素流；即使中继被入侵，业务凭据/遮罩区域不可还原（合成器逻辑 v0.2 已在跑，本方案不引入新的隐私面） |
| D3 | P2P 优先（`iceServers:[]` 局域网直连 / 公网配 STUN），**>5 观众切换 SFU** | ≤5 人（绝大多数客户演示）零额外依赖；公网大规模走 LiveKit Cloud 或自托管 SFU（中继拉起 sidecar，复用 v0.1 的 JWT/权限设计） |
| D4 | 房间模型：**房间码 + 令牌**。演讲者创建房间得到 `presenterToken` + 观众链接；观众链接内含 `viewerToken`（不可猜测、会话结束即失效） | v0.1 已验证该模型；公网暴露面最小化——无账号体系，令牌即权限 |
| D5 | 观看页由**中继托管**（静态 HTML，WebViewer 单页） | 观众零安装；与 v0.1 观众页同构（SSE 快照 + WebRTC 订阅），可大量复用设计 |
| D6 | 扩展侧复用 v0.2 管线：offscreen 发布端从"本机回环 peer"改为"中继信令 peer"，**合成器/捕获/授权路径零改动** | 把改动压缩在"信令与房间管理"层；本机观众窗口继续走现有回环，不经过中继 |
| D7 | 信令协议沿用 v0.1 P2P 消息集（join/offer/answer/ice/leave + quality preference） | 协议已过实战验证；中继仅做中转不做媒体处理 |

## 3. 组件设计

### 3.1 中继服务 `apps/relay`（新）

- **栈**：Node 22 + TypeScript + `ws` + 轻量 HTTP 框架（无重依赖；SFU 模式才引入 `livekit-server` sidecar）
- **REST**（供扩展后台调用，需 `presenterToken`）：
  - `POST /api/rooms` → `{ roomCode, viewerUrl, presenterToken, signalUrl, sfu }`
  - `DELETE /api/rooms/<code>` → 结束房间、踢出全部观众
  - `GET /api/rooms/<code>/viewers` → 在线观众/状态
  - `POST /api/rooms/<code>/kick/<viewerId>` → 断开单个观众
- **观看页** `GET /watch/<code>`：单页应用（原生 JS，无构建或 vite 预构建产物直接托管）；SSE 拉会话快照（页码/品牌/遮罩/离线状态），WebRTC 订阅合成流
- **信令** `WSS /signal/<roomCode>/<token>/<role>/<peerId>`：纯中转（校验令牌后按 peer 转发，不解析 SDP）
- **SFU 模式**：房间创建时 `capacity=sfu` → 中继按需拉起 livekit-server（随机端口、JWT HS256：publisher 仅 canPublish / viewer 仅 canSubscribe，复用 v0.1 `SfuManager` 设计）
- **生命周期**：房间空闲 15 分钟自动回收（防止"忘记结束"导致公网裸奔）；进程内状态，重启即清（与"会话即房间"模型一致）

### 3.2 扩展侧改动（最小化）

| 文件 | 改动 |
|---|---|
| `messaging/protocol.ts` | `open-remote-audience { relayBase, capacity }` / `end-remote`；广播元数据增加 `remote: { roomCode, viewerUrl, viewerCount }` |
| `entrypoints/background.ts` | 房间生命周期（创建/结束/状态轮询/踢出）；观众计数并入现有 `set-audience-count`；`endSession` 无条件关房间 |
| `entrypoints/offscreen/main.ts` | 发布端抽象：`LoopbackPublisher`（现状）+ `RelayPublisher`（WSS 信令 + RTCPeerConnection，公网附加 STUN）；二者可并存（本机窗口 + 远程观众） |
| `entrypoints/sidepanel/` | 设置抽屉：中继地址（`chrome.storage.local` 记忆）、容量模式；"远程观众"开关 + 观众链接复制 + 二维码（复用 v0.1 qrcode 依赖思路，原生生成） |
| `entrypoints/workbench/` | 项目设置暴露中继默认地址（按项目记忆） |

**明确不改**：合成器、tabCapture 授权手势、demo 镜像、步骤执行、遮罩/标注管线。

### 3.3 观众侧体验（对齐"观众只看系统"）

- 打开链接即看画面（无登录、无安装）；页码/品牌角标同本机观众屏
- 演示者侧控制台显示"本机 N + 远程 M"两级计数；可断开单个/全部远程观众
- 连接质量自适应（v0.1 的 preference 机制：低带宽自动降码率/缩放）

## 4. 部署形态

| 场景 | 部署 | 观众访问 |
|---|---|---|
| 局域网 | `docker run -p 8080:8080 showit-relay`（或裸 `node`） | `http://<内网IP>:8080/watch/<码>` |
| 公网 | 云主机 + 域名 + TLS（caddy/nginx 反代，WSS 透传） | `https://demo.example.com/watch/<码>` |
| 临时公网 | 本机起服务 + 云隧道（frp/cloudflared） | 隧道域名 |

中继无持久化、无账号，升级=替换进程；`Dockerfile` + `docker-compose.yml`（含 SFU sidecar profile）随仓库交付，CI 产出 `showit-relay` 镜像工件。

## 5. 测试与验收

- **单测**：中继房间/令牌/信令转发/自动回收；扩展发布端信令状态机；协议类型
- **集成（Node 层）**：中继 + headless 双浏览器（Playwright）：创建房间 → 观看页连接 → 收到合成流（`videoWidth>0`）→ 断开/回收
- **扩展 E2E 扩展**：`test:extension-remote-e2e` —— 起本地中继 → 演示启动远程观众 → 观众页收到画面（业务页路径）→ 结束清理（房间 404）
- **公网验收（人工，纳入发布文档）**：真实云部署 + 跨网观众 + 弱网降级 + 手机浏览器观看
- **安全清单**：令牌不可猜测（128bit）/房间码限速创建/观看页 CSP 收紧/信令消息尺寸上限/SFU token 最小权限/中继不记录观众 IP

## 6. 范围裁剪（相对 v0.1 观众服务）

1. 观众审批流**保留**（direct/approval 两种，项目级配置沿用现有字段）；踢出保留；**质量统计面板**降级为"连接状态徽标"（详细 getStats 仪表留待需要时）
2. 网络接口选择（v0.1 用于绑定特定网卡）不恢复——公网模型下无意义，局域网由部署位置决定
3. 观众端聊天/表情等互动能力不做（观众只看不说的产品红线）

## 7. 实施步骤

1. `apps/relay` 骨架：HTTP + 房间/令牌 + 观看页静态托管 + 单测
2. 信令 WS（P2P 转发）+ SSE 快照通道
3. 观看页（SSE + WebRTC 订阅，遮罩/封面状态同步）

8. 公网人工验收清单执行

## 8. 自评审记录

**Q1 公网暴露的安全边界？**
三道门：观看链接令牌（不可猜测 + 会话失效）、源端合成（中继只见已保护画面）、房间空闲回收 + 创建限速。中继无账号无持久化，被攻破的影响面=一个已结束演示的像素流转发。验收清单含 CSP/尺寸上限/日志红线。

**Q2 为什么不用 WebRTC 一体化云服务（LiveKit Cloud 等）？**
企业客户（售前演示）常在内网/私有环境，"自托管优先"是产品定位；同时保留云托管选项——中继的 SFU 模式可指向 LiveKit Cloud，架构不锁死。

**Q3 观看页托管在中继，公网观众页会被浏览器混合内容拦截吗？**
中继统一 TLS（WSS/HTTPS 同源），观看页与信令同源无混合内容；局域网 HTTP 全程同源。

**Q4 扩展在公网模型下还需要 STUN，这违反"无公网依赖"红线吗？**
v0.1 红线是"局域网投送不依赖公网 STUN"。v0.3 明确新增**公网观众**能力，公网链路使用公网基础设施是题中之义；局域网路径保持 `iceServers:[]` 纯内网。两模式按部署形态显式区分并写入文档。

**Q5 与本机观众窗口并存会不会复杂化 offscreen？**
两个 Publisher 实例独立（回环 peer 不经中继），故障域隔离；观众计数合并展示。风险可控，已在 D6 明确。

**Q6 中继 Node 而非复用 v0.1 Rust？**
Rust 服务绑死在 Tauri 桌面壳内（axum + 原生进程管理），抽出为独立交付单元的迁移成本高于用现有 TS 栈按蓝图重写；团队栈统一、Docker 产物更小。v0.1 代码作为协议与安全设计的参照实现保留在 git 历史。

**结论：方案通过，按 §7 实施。**
