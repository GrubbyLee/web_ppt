# Showit 技术栈和开发框架（脚手架）选型

> 文档用途：技术评审与开发启动基线
> 评审日期：2026-09-12
> 适用产品：Showit 演示工作台

## 1. 选型结论

Showit 采用以下技术栈：

| 层次 | 选型 | 选型理由 |
|---|---|---|
| 前端语言 | TypeScript 5.x | URL、脚本、同步事件、会话和页面状态需要强类型约束 |
| 前端框架 | React 19 | 生态成熟，适合编辑器、复杂运行时和可复用组件共存 |
| 应用脚手架 | Vite 8 + React + TypeScript | 启动快、构建简单，适合纯 Web 应用和独立演示运行时 |
| UI 组件体系 | Ant Design 5 + `@ant-design/pro-components` | 项目管理、配置表单、表格、抽屉、弹窗和状态反馈可直接复用 |
| 路由 | React Router 7 | 编辑器、项目详情、运行时和观众屏需要明确 URL 路由 |
| 服务端状态 | TanStack Query 5 | 请求缓存、失效、重试、加载和错误状态统一处理 |
| 客户端状态 | Zustand | 演示会话、计时、标注、布局和观众屏状态需要轻量跨组件共享 |
| 页面编排 | `@dnd-kit` | 页面排序、拖拽和键盘操作支持完整，适合编辑器 |
| 可拖拽分栏 | `react-resizable-panels` | 中左/中右区域需要拖拽、键盘调整和比例持久化 |
| Markdown | `react-markdown` + `remark-gfm` + `rehype-sanitize` | 支持 GFM 语法并在渲染边界完成清理 |
| 表单校验 | Zod + React Hook Form | 项目、连接器、页面和脚本配置需要共享 Schema |
| 图标 | `@ant-design/icons`，必要时 Lucide React | 与 Ant Design 组件风格一致，补充演示运行时图标 |
| 动画 | CSS transitions，必要时 Motion | 运行时只保留与状态和焦点有关的动效，避免动画干扰演讲 |
| 测试 | Vitest + Testing Library + Playwright | 单元、组件、浏览器交互、双屏和真实 URL 回归分层覆盖 |
| 服务端 | Node.js 22 LTS + Fastify | API、SSE/会话事件和代理服务轻量，TypeScript 类型可共享 |
| 数据库 | PostgreSQL 16 | 项目、版本、页面、脚本、连接器、会话和审计需要事务与版本控制 |
| 缓存/协调 | Redis 7 | 会话短状态、nonce、防重复提交和观众屏协调 |
| 对象存储 | S3 兼容存储 | 封面、离线备份、脚本导入导出和演示资源 |
| 部署 | Docker Compose（开发）/ Kubernetes（生产可选） | 开发环境简单，生产可按规模选择编排方式 |

推荐的应用脚手架是 **Vite + React + TypeScript + Ant Design Pro Components**。Ant Design Pro 的管理类组件用于项目编辑器和配置工作区；演示运行时的四区布局、iframe、计时、标注和观众屏属于产品核心交互，使用 React 组件和浏览器 API 实现，不强行套用管理后台页面模板。

## 2. 选型原则

- 运行时优先保证演示稳定，编辑器优先保证配置效率。
- 采用可替换的连接器和脚本合同，不把业务系统 DOM 结构写死在 Showit。
- 组件库负责通用交互和状态反馈，业务编排组件由 Showit 自己维护。
- 浏览器只访问 Showit API；业务页面通过连接器和受控 iframe/代理访问。
- 设计令牌、组件命名和状态枚举先固化，再开始页面实现。
- 所有项目配置支持版本、审计和回滚；运行时只能使用已发布版本。

## 3. 候选方案比较

### 3.1 React + Vite + Ant Design Pro Components

优点：

- Ant Design 的表单、列表、表格、抽屉、弹窗、通知、步骤条和结果反馈成熟，能覆盖项目编辑器的大部分界面。
- React 生态对 iframe、拖拽、Markdown、面板尺寸、键盘事件和双窗口通信支持充分。
- Vite 不绑定 SSR 和特定部署平台，演示运行时可以作为静态资源部署。
- TypeScript 类型可以贯穿前端、Node BFF、Schema 和测试。

需要控制的点：

- Ant Design Pro Components 不应覆盖演示运行时的深色控制台视觉；运行时需要独立的 Showit Design Tokens。
- ProTable、ProForm 只用于编辑器和管理页面，不能把业务 iframe、备注和计时器塞进表格模型。
- 需要约束依赖数量，避免每个功能引入一个同类库。

### 3.2 Vue 3 + Vite + Element Plus

优点：

- Element Plus 的后台组件完整，Vue 单文件组件容易上手。
- Vite、TypeScript 和 Playwright 生态同样成熟。

不足：

- 当前团队已有 React + Ant Design Pro 经验和代码资产，迁移成本较高。
- 对复杂跨窗口会话、可配置运行时和编辑器状态的生态积累不如 React 统一。
- 如果采用 Element Plus，需要重新建立一套与现有产品资产无关的组件约束。

### 3.3 Next.js + React + MUI

优点：

- 路由、服务端渲染、部署和内容页面能力完整。
- MUI 的主题和无障碍基础较好。

不足：

- Showit 的核心是客户端演示运行时，SSR 对 iframe、计时、第二窗口和 BroadcastChannel 没有直接收益。
- MUI 与现有 Ant Design Pro 资产不兼容，项目编辑器需要重新补齐大量 Pro 级业务组件。
- Next.js Server Actions、缓存和运行时模式会增加部署与调试约束。

### 3.4 结论

选择 React + Vite + Ant Design Pro Components。Vue 方案的能力足够，但会放大团队迁移和组件资产重建成本；Next.js 方案适合内容型或 SSR 产品，和 Showit 的客户端演示工作流不匹配。

## 4. 服务端框架比较

### 4.1 Fastify + TypeScript

Fastify 作为 Showit BFF 和领域 API 的默认框架。它的请求生命周期、插件机制、Schema 校验和日志钩子足够支撑项目 API、SSE、健康检查和受控代理；前后端可以共享 TypeScript 类型和 Zod Schema。演示运行时不需要服务端渲染，Fastify 的轻量模型更适合独立部署和故障隔离。

### 4.2 NestJS

NestJS 的模块、依赖注入和装饰器适合大型团队的复杂后端，但会带来更多运行时抽象和样板代码。若后续把项目权限、组织、计费和审计扩展成多团队平台，可以在 Fastify Adapter 之上采用 NestJS；第一阶段不需要为此引入额外层次。

### 4.3 Go（Gin/Fiber）

Go 的并发和单二进制部署有优势，但会打断前后端 TypeScript 类型共享，Markdown、URL、项目 Schema 和测试需要维护两套类型。Showit 的性能瓶颈主要在外部业务页面和浏览器渲染，第一阶段不值得为此切换语言。

### 4.4 服务端结论

选择 Fastify + TypeScript。将项目、连接器、会话和排练按插件/模块拆分，使用 OpenAPI 与 Zod Schema 生成合同。若后续出现 CPU 密集的媒体处理或高吞吐代理，再将独立服务拆为 Go，不改变前端合同。

## 6. 关键依赖边界

### 5.1 Ant Design Pro Components

用于：项目列表、项目详情、版本、页面配置表单、连接器配置、权限、发布确认、演前检查和异常状态。

不用于：业务 iframe 内部页面、演讲者备注编辑器的核心布局、标注画布和观众屏覆盖层。

### 5.2 TanStack Query 与 Zustand

- TanStack Query 保存项目、页面、脚本、连接器和版本等服务端数据。
- Zustand 保存当前演示会话、当前页、计时、布局比例、标注和屏幕状态。
- 同一数据不在两套状态中重复维护；服务端数据变更通过 Query invalidate 通知页面刷新。
- 会话状态刷新后从服务端快照恢复，临时激光点等短状态只通过同步事件传递。

### 5.3 Markdown 渲染

- 编辑器保存 Markdown 原文。
- 运行时使用 `react-markdown` 和 `remark-gfm` 渲染。
- 通过 `rehype-sanitize` 或 DOMPurify 清理 HTML。
- 禁止脚本、事件属性、任意 iframe、`javascript:` URL 和未登记外链协议。
- 代码块、表格、链接和标题使用 Showit 运行时 Token，不复用业务系统 CSS。

### 5.4 iframe 与业务连接器

- `BusinessFrame` 只接受经过 Zod 校验的 Connector 配置。
- 默认 `sandbox="allow-scripts allow-same-origin"`，登录确有需要时才加入 `allow-forms`。
- 会话消息校验 `origin、source、sessionId、seq、nonce`。
- 连接器策略决定 GET/HEAD/OPTIONS、登录/退出和业务写操作是否放行。
- Showit 不读取跨源业务页面 DOM，不依赖业务页面的 CSS 类名。

## 7. 服务端与数据层

服务端采用 Node.js 22 + Fastify，按以下模块拆分：

- `project-service`：项目、页面、脚本和版本。
- `connector-service`：URL 校验、健康检查、只读代理和连接器策略。
- `session-service`：演示会话、观众屏握手、事件快照和过期处理。
- `rehearsal-service`：计时、排练记录和导出。
- `audit-service`：发布、连接器变更、权限和运行异常。

核心表：`projects`、`project_versions`、`pages`、`scripts`、`connectors`、`sessions`、`session_events`、`rehearsals`、`audit_events`。

所有写操作使用 `Idempotency-Key`；项目编辑和发布使用 `ETag/If-Match`。脚本内容、URL 和事件日志不保存 Cookie、Token、Secret 或完整业务响应体。

## 8. 脚手架初始化基线

建议命令：

```bash
npm create vite@latest showit-web -- --template react-ts
cd showit-web
npm install antd @ant-design/icons @ant-design/pro-components
npm install react-router @tanstack/react-query zustand
npm install @dnd-kit/core @dnd-kit/sortable react-resizable-panels
npm install react-markdown remark-gfm rehype-sanitize zod react-hook-form
npm install -D vitest @testing-library/react @testing-library/jest-dom playwright
```

版本管理要求：

- Node.js 固定 22 LTS，使用 `.nvmrc` 或 Volta 固定版本。
- 依赖使用 `package-lock.json`，CI 使用 `npm ci`。
- 生产构建启用 TypeScript `noEmit` 检查、ESLint、依赖审计和 Bundle 预算。
- 不在业务代码中直接引用 Ant Design 内部实现；仅使用公开 API。
- `BroadcastChannel`、`postMessage`、`ResizeObserver` 和 `requestFullscreen` 均提供浏览器不支持时的降级路径。

## 9. 测试与质量门禁

| 门禁 | 工具/方式 | 关键检查 |
|---|---|---|
| 类型检查 | `tsc --noEmit` | API、事件、状态和组件 props 无隐式 any |
| 单元测试 | Vitest | URL 校验、变量替换、计时、消息去重、状态机 |
| 组件测试 | Testing Library | 表单、Markdown 清理、分栏、按钮状态和错误态 |
| 浏览器测试 | Playwright | 编辑项目、拖拽页面、编辑脚本、运行演示、观众屏和排练 |
| 安全测试 | Playwright + API 测试 | XSS、恶意 URL、跨源消息、只读代理绕过和敏感值输出 |
| 视口回归 | Playwright screenshot | 1440×900、1024×768、375×812 无溢出和遮挡 |
| 构建门禁 | Vite Bundle Analyzer | 首屏外壳和编辑器分包，限制初始 JS 体积 |

每个页面至少覆盖 `Loading、Empty、Error、Forbidden、Conflict、Success`；演示运行时还要覆盖业务页面未登录、角色不匹配、观众屏断开和同步恢复。

## 10. 部署方式

开发环境：

- `showit-web`：Vite dev server，监听 `0.0.0.0`。
- `showit-api`：Fastify dev server。
- PostgreSQL、Redis、对象存储使用 Docker Compose。
- 业务系统只读代理单独部署，不与 Showit 前端共享写权限。

生产环境：

- 前端静态资源由 Nginx/CDN 提供，API 由 Fastify 服务提供。
- API、PostgreSQL、Redis 和对象存储使用独立网络和凭据。
- 运行时业务代理与项目管理 API 分离，避免业务页面访问管理接口。
- 观众屏不保存项目编辑权限，只持有短期 sessionId。
- 日志输出 traceId、项目版本和会话 ID，不输出业务凭据。

## 11. 实施顺序

1. 初始化 Vite/React/TypeScript 工程，建立 Token、Schema、路由和错误边界。
2. 先抽离运行时四区和当前 18 页黄金样例，确保计时、备注、观众屏、标注和同步功能完整。
3. 加入项目、页面、脚本和连接器 API，替换运行时中的硬编码配置。
4. 加入拖拽编排、Markdown 编辑、版本发布和权限。
5. 加入只读代理、健康检查、异常恢复和安全门禁。
6. 完成 Penpot 新设计后实现视觉层，保留运行时交互合同。
7. 执行浏览器、双屏、视口、安全和迁移回归，最后再切换产品入口。

## 12. 不选用的技术

- 不以 Electron 作为第一阶段运行容器；先完成浏览器版，只有需要系统级多屏控制、离线资源和窗口管理时再封装桌面壳。
- 不使用 iframe 内嵌业务系统的 DOM 自动化作为核心协议；业务系统只通过 URL、连接器和明确消息合同接入。
- 不使用重量级全局状态框架；会话状态和服务端数据分别由 Zustand、TanStack Query 管理。
- 不使用未维护的 Markdown HTML 注入方案；所有渲染必须经过白名单清理。
